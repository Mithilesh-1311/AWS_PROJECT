# Vercel frontend + Render backend

Prepared for deployment; no service has been created or uploaded. Existing local and AWS Compose configurations remain available.

## Architecture and cost

Vercel serves the React/Vite frontend. The browser calls the Render HTTPS API and connects directly to its WSS replay endpoint. There is no Vercel API proxy or WebSocket server.

`render.yaml` uses a **paid Standard web service** with a **10 GB persistent disk**. Review the current price before creating it. API and training worker run as separate processes in that one service because the existing SQLite queue and models require the same filesystem. Render disks cannot be shared between services. Run one service instance; scaling requires a different queue/storage design. Standard is an initial memory choice, not a measured capacity guarantee for full training.

The disk stores `/var/data/dataset` (containing S1 through S14) and `/var/data/artifacts` (experiments, models, state, cache, reports). Render supplies the HTTP `PORT`; the launcher starts one Uvicorn worker plus the existing training worker and stops both if either exits. Deployment or restart interrupts active training; the queue's existing lease recovery marks interrupted jobs failed.

## Settings to enter at deployment

| Platform | Setting | Value |
| --- | --- | --- |
| Render | Blueprint | Repository root `render.yaml` |
| Render | `EOG_ALLOWED_ORIGINS` | Exact Vercel production origin, e.g. `https://your-project.vercel.app`, without a trailing slash |
| Render | `EOG_ACCESS_TOKEN` | Generated by the Blueprint; retrieve privately in Render's Environment settings |
| Vercel | Root Directory / framework | `frontend` / Vite |
| Vercel | Build / output / Node | `npm run build` / `dist` / 22.x |
| Vercel | `VITE_API_BASE` | `https://YOUR-SERVICE.onrender.com/api` |

Python 3.10 is selected by `backend/.python-version`, matching the existing runtime. `frontend/vercel.json` supplies SPA fallback routes and response headers. API URL changes require a frontend rebuild. Set the Vercel production origin in Render once its URL is known; additional allowed origins are comma-separated exact origins. Preview deployments require explicit allowlisting; do not allow `*.vercel.app`.

No secrets belong in `VITE_*`, Git, screenshots or deployment logs. Users enter the Render access token in the sign-in form. It is retained in that browser tab's session storage and cleared on sign-out or an HTTP 403. This is shared owner access: anyone with the token can run jobs and activate models. Rotate the Render token to revoke it. The existing Caddy proxy authentication remains supported for AWS/local Compose.

REST calls and exports use the Authorization header. Browser WebSockets carry the token as a proposed `eog-token.*` subprotocol and negotiate only `eog-replay`; no token goes in a URL. Do not enable request-header logging that would capture Authorization or Sec-WebSocket-Protocol.

## Dataset and serving model

The dataset and generated serving models are excluded from Git. An initial deploy can display published reports but cannot predict or replay until both are installed. Transfer only data you are authorized to host. No automatic data upload is included.

1. After the service exists, transfer the trusted dataset through Render SSH/SCP to `/var/data/dataset`, with `S1` through `S14` directly inside it. See Render's disk transfer instructions below. Do not commit the archive or create a public download link.
2. Transfer the trusted active experiment directory from local `backend/artifacts/experiments/<experiment-id>` into `/var/data/artifacts/experiments/<experiment-id>`. It needs the matching `model.json`, `serving.joblib`, and experiment files. Transfer only project-produced model binaries with the pinned dependency versions; loading an untrusted joblib file can execute code.
3. In the Render Shell (working directory `backend`), activate its model ID:

   ```sh
   python -c "from app.models.registry import activate; activate('<model-id-from-model.json>')"
   ```

4. Restart the service after installing the dataset: dataset discovery happens when Python imports the configuration. Sign in and confirm that the dataset, model and worker indicators are ready. Keep immutable experiment directories together; never copy a live SQLite database as a backup.

Alternatively, train a compatible model in Render Shell after the dataset is installed, using the training command in the README. This consumes service memory and CPU alongside inference. Use the compatible causal logistic serving model; the optional TCN dependencies are not installed by this deployment.

## Verification before going live

Local preparation checks passed: frontend lint and production build, 17 backend tests (including auth/CORS/replay and launcher lifecycle), one browser sign-in/export/sign-out test with a mocked external API, and three existing browser boundary tests. Deployment JSON/YAML syntax was checked locally; Render's cloud Blueprint validation has not been run. Cloud resources, Linux native dependency installation, real disk permissions, upload, and cloud inference still need verification during deployment.

Backend tests, from `backend`:

```sh
python -m pytest -q tests/test_render_deployment.py tests/test_research_services.py tests/test_api.py
```

Browser deployment test: start Vite with `VITE_API_BASE=https://eog-api.example/api` on port 5180, then run Playwright with `EOG_TEST_REMOTE_API=1` and `EOG_TEST_URL=http://127.0.0.1:5180`. The API is explicitly mocked; no external service or credentials are needed. CI runs this alongside the existing boundary tests.

After deployment, verify: `/api/health` works without a token; other API endpoints reject missing/wrong tokens; sign-in succeeds from the allowlisted Vercel origin; direct navigation to `/reports` works; JSON/CSV/printable reports export; a known prediction and recorded WSS replay match; the worker completes a smoke job; a controlled restart preserves artifacts and model activation. Back up artifacts and use SQLite's backup API before upgrades.
